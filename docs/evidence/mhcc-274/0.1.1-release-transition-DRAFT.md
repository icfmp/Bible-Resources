# BRMHCC 0.1.1 — version migration and rollback (draft)

**No new release, no content change, no owner publication approval.**
This is a technical transition specification for a future approved
release, not an activated release plan or catalogue entry.

## One live identity

Keep the existing `modules/mhcc-crosswire` directory,
`mhcc-crosswire` curated ID, `BRMHCC` SWORD ID and
`matthew-henry-concise-crosswire-2.0` canonical source lineage.
Once a real final approved candidate exists, update the current
metadata/version to 0.1.1 and replace only this module's live payload.
The compiled format remains standard SWORD `zCom` with KJV
versification; newly compiled data use `BlockType=CHAPTER`.

There is still only **one** live catalogue entry and **one**
`BRMHCC.zip` Pages download URL. Changing that current URL's bytes
is a normal *versioned update*, not permission to overwrite the
previous versioned GitHub Release.

## Plan and descriptive profile transition

The current active plan is `config/release-plans/mhcc-0.1.0.json`,
not a legacy-binding record. It must be **removed from the current
plan directory** when an approved `mhcc-0.1.1.json` plan is added.
Two active plans for the same module fail closed. The previous plan
persists in immutable Git history, and GitHub release
`mhcc-0.1.0`/`BRMHCC-0.1.0.zip` remains available for rollback.

The existing English reader profile is approved specifically for
version 0.1.0 and claims that original source words and references
are untouched. The current schema rejects that approval when the
module version advances. Publish 0.1.1 with a **new separately
approved description** based on
[the draft](0.1.1-reader-profile-DRAFT.md), or omit the optional
profile until approved. Do not re-label the 0.1.0 approval as current.

## Checks before owner release authorization

1. Independently approve exact authorial correction scope and
   CrossWire source/rights, avoiding any import of separately
   digitized CCEL text or editorial markup.
2. Choose the *actual* 0.1.1 publication date. The last passing
   private rehearsal used a **hypothetical date** and its ZIP SHA
   is deliberately **not a release checksum**.
3. Rebuild and verify the complete native original/updated corpus:
   28,718 original K and 24 reviewed aliases, 1,255 I, 2 TOP;
   exactly 12 original K addresses affected by two source-body edits,
   and all original SWORD linked boundaries unchanged.
4. Commit only the **independently reviewed final seven SWORD files**
   and complete source-attested version-specific proof and rights
   metadata, not scratch test binaries. Recompute the deterministic
   `scripts/build.py` package hash and size from the final files.
5. Update the single current catalogue entry, attach the *new*
   authorized release plan `mhcc-0.1.1` with matching final ZIP
   hash/size, and approve a new version-specific reader description
   or intentionally omit the optional profile.
6. Obtain **express separate owner authorization** for merge,
   immutable release and Pages update. On publication, the
   GitHub Release must be created/verified before Pages changes.
7. Independently verify the old `mhcc-0.1.0` release still downloads
   with its originally pinned SHA-256 and size. Verify the new
   versioned release and stable Pages ZIP separately. If recovery
   is necessary, the versioned old asset is the original rollback
   specimen; app installation policy belongs to the Bible app repo.
