# Independent native stable-SWORD reference inventory

This is **the second input producer** for the generic [verse-index audit](STABLE_SWORD_REFERENCE_AUDIT.md). Unlike the separately [source-authored OSIS key producer](SOURCE_OSIS_INVENTORY.md), it asks the **real installed released libSWORD engine**, using the module's own native `VerseKey` and `hasEntry`, which numbered keys are actually addressable. It also enumerates every chapter's registered native verse ceiling (including empty slots) and detects occupied `book.0.0` / `book.chapter.0` introduction records.

It works on ordinary Bible SWORD `RawText` and `zText` module drivers without encoding any edition title, fixed verse count or custom versification; *actual integration* has so far only been independently checked against our existing LSG RawText release. A second unrelated zText Bible remains an acceptance criterion in #28.

## Compile and collect (isolated, no Scripture output)

Use the **released stable** system `libsword-dev` and `diatheke` packages. First install a **single module** into a local isolated `modules/<id>/payload/mods.d` + `modules/...` root, preserving the exact compiled package bytes.

```sh
g++ -std=c++17 -O2 -I/usr/include/sword \
  scripts/sword_native_index.cpp -o /tmp/sword-native-index -lsword

mkdir -p /tmp/native-sword-proof
python scripts/sword_native_inventory.py \
  --inspector /tmp/sword-native-index \
  --module-directory modules/lsg-1910 \
  --module-id BRLSG1910 \
  --reader-keys-output /tmp/native-sword-proof/native-keys.txt \
  --registry-tsv-output /tmp/native-sword-proof/native-registry.tsv \
  --report /tmp/native-sword-proof/native-proof.json
```

The values above illustrate the **already published LSG module** in this repository. Replace every module and path to inspect a different, rights-cleared edition; the Python/C++ tools do not hardcode them. No new release or source data is generated by this command.

The isolated `SWORD_PATH` is set to the **same verified payload** for which the whole module SHA-256 digest is calculated; the resulting source-independent text-free inventories are bound to that digest and the trusted compiled inspector digest. The reporter rejects missing module/driver/versification, unfamiliar native runtime, out-of-registry/duplicate/unordered keys, malformed end-of-scan counters and unsafe/conflicting output paths. Its only contents are verse IDs and metadata; no biblical text/notes are printed.

## Combining independently produced source and reader indexes

When—and only when—you have an independently schema-validated OSIS source and separately reviewed publisher/source edition identity:

```sh
python scripts/stable_sword_refs.py \
  --source-keys /tmp/source-keys.txt \
  --resolved-reader-keys /tmp/native-sword-proof/native-keys.txt \
  --registry-tsv /tmp/native-sword-proof/native-registry.tsv \
  --versification Segond \
  --reader-version 1.9.0 \
  --source-osis-sha256 <SHA256_OF_THE_VALIDATED_OSIS> \
  --module-directory modules/lsg-1910 \
  --report /tmp/native-sword-proof/comparison.json
```

**Do not literally reuse** `1.9.0`, the sample paths, or the example versification for other modules; take the real engine version, native scheme and source SHA from independently validated receipts. Source-reviewed adjacent final-key merges also need the separately attached immutable owner-authorized policy and full independent chapter-body readback. The comparison report defaults reviewer approval to `PENDING`; **it does not approve or publish the resource**.

### Independent scope and caveats

- This producer inspects the actual **native installed keys**, unlike querying source keys and treating a successful compiler exit as proof. A module with a misleading declared v11n may have internally valid native keys yet remain *wrongly addressed relative to its publisher*; the independent source comparison must catch that.
- Empty source/editorial slots are not synthesized. A stock SWORD registry can contain an unused key; those are listed in the registry but not in occupied keys.
- Intro keys are included in the native JSON receipt but never in the ordinary source-key TSV, which only accepts positive numbered verses. Their **text, note anchors and ordered markup** still require independent full-corpus checks.
- `hasEntry` proves stored, native-indexed entry **occupancy**, not authorial word/string identity, label visibility, note rights, appropriate visual layout or JSword/AndBible parity.
- The stock SWORD native module and installed registry require an **independently attested immutable edition/source chain**, as for the approved LSG archive. Human source and editorial approval cannot be inferred from the presence of keys.

The normal CI now builds the C++ inspector with system `libsword-dev`, runs it on the actual published `BRLSG1910` bytes, and compares the **observed real native occupied-key and chapter counts** to the source-pinned original reader audit. This test does not approve a replacement module or claim zText integration proven. The next tasks in [#28](https://github.com/icfmp/Bible-Resources/issues/28) are the first independent zText edition and full text/lexical/note/ordered-structure comparisons.
